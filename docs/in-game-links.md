# In-game Show Info links

The Overview ends with a quiet optional support card. EQM remains free software; clicking **Steihl Lianul** opens a character picker, then a reference mail draft on the selected logged-in EVE character. The draft contains a large green clickable Character Info link to Steihl Lianul and the optional donation reason **EQM**. No mail is sent and no ISK is transferred.

Item names have a small **↗ Open in EVE** action across asset/inventory/ship reports, D-Scan, Market, fittings and modules, blueprints/recipes, industry/PI, exchange, ship/combat displays, and other typed item lists. Existing filter, market-history and external-link clicks remain intact. Where the name already belongs to such a control, right-click its item label or focus the control and press **Alt+Enter**. Ordinary owned blueprint names also open the picker directly; hover still shows blueprint details and Alt+Enter/right-click work there too. Select controls, free text and exported PDFs are not turned into game controls. Unauthenticated public-report viewers see ordinary text.

Owned blueprint links use the server's authorized Blueprint/Asset row, including its real EVE item ID when available: `showinfo:<typeID>//<itemID>`. The preview and draft include synced BPO/BPC kind, ME, TE and BPC remaining runs. Manual records, research shadows without a retained asset ID, generic recipe/BPO references and anonymous report rows use `showinfo:<typeID>` instead. Public reports never gain private item IDs or owner identities for this integration. The server validates current record visibility again before opening a draft. IDs and efficiencies cannot be supplied or forged by the client.

EVE decides whether the selected pilot can inspect a particular instance; an EQM visibility grant does not grant in-game ownership or corporation rights. ME/TE and runs in the draft are the latest synchronized EQM values. This implementation follows the instance-link format used by RIFT; it does not encode invented ME/TE fields in a generic type link. Client rendering of instance details still needs an in-game check on a real owned BPO/BPC.

## Consent and privacy

Only the current account's own non-revoked, currently owned character tokens can open windows—even administrators cannot select another account's client. `esi-ui.open_window.v1` is sufficient; mail read/send/organize scopes are not requested for this feature. A missing-scope character offers explicit EVE SSO consent for in-game windows. The flow keeps already granted, currently role-permitted integrations and adds only this UI permission. It is bound to the selected existing character; authorizing another pilot is rejected before changing ownership or credentials. Account-login SSO and ordinary utility-only enrollment remain identity-only. The UI permission belongs to the utility scope set and does not enable private asset/skill collection.

Drafts are addressed to the selected character itself so they can use the included Show Info link. All game-window calls require an explicit **Open draft in EVE** click. The server uses `/ui/openwindow/newmail/`, never the send-mail endpoint, and the UI prevents duplicate clicks while waiting. EVE must be running with that character logged in. After an uncertain ESI timeout, check the client before retrying.

API: `GET /client-links/characters`, `GET /client-links/characters/{token_id}/auth-url`, `POST /client-links/preview`, `POST /client-links/draft`. Draft requests allow only target kind, type ID/exact SDE name, authorized internal blueprint/asset row ID and own token ID; arbitrary HTML, recipient lists and EVE item IDs are rejected. Preview/character/consent responses are private and non-cacheable. EVE HTML labels escape &, < and > without unsupported quote entities. Exact 64-bit item identifiers stay server-side.

## Verification and rollout

New tests cover exact BPO/BPC links and efficiencies, large item IDs, generic/manual fallback, private/other-owner records, own-character isolation even for administrators, transfers/revocation, missing scope, minimal/preserved consent, utility-only collection, character-bound consent, canonical previews, HTML escaping, payload spoof rejection, real Quartermaster authentication, and upstream failures. Existing scope, Quartermaster, combined-role and account-SSO checks also pass. A stale Quartermaster test expecting personal profile edits to fail was corrected to match the already-existing profile utility exception, with explicit positive coverage.

TypeScript and production build pass. Browser verification uses the actual built UI on isolated SQLite at localhost:8787, synthetic accounts/holdings and a mocked ESI draft endpoint. Creator and blueprint draft payloads, picker consent state, keyboard opening, focus restoration, and the optional card placement were inspected. No real EVE windows, messages, ISK transfers, production accounts or data were touched. Matching API/frontend rollout is required; no new migration or version bump for these links. Other pending features may have their own migration requirements.

Protocol references: [CCP-hosted EVE HTML guide](https://developers.eveonline.com/docs/guides/eve-html/) and [RIFT's published source](https://riftforeve.online/source.html), inspected for the link format only; no RIFT implementation code was copied.
